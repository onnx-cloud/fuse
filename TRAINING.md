# @train/@frozen Implementation

## Overview
The `@train` and `@frozen` decorators provide a way to mark parameters and constants as trainable or non-trainable (trainable) in Fuse. 

### Syntax
```fuse
@training {
  optimizer:
    type: adamw,
    lr: 0.0003
  schedule:
    type: cosine,
    warmup: 1000,
    steps: 100000
}
@train weight w: f32[features,64]
@frozen weight f: f32[2] = [0,1] @import="frozen.onnx"
```

### Semantics
- **`@training {...}`**: Module-level metadata block specifying training configuration (optimizer, schedule). Parsed as a metadata entry with `name="fuse.training"` and structured value.
- **`@train param_decl`**: Marks a parameter or weight as **trainable** (`trainable=True`).
- **`@frozen (param_decl | const_decl)`**: Marks a parameter or constant as **frozen** (`trainable=False`).

### Design Invariant
Both decorators are **syntactic sugar** that attach a `trainable` boolean flag to the AST node for downstream consumption. Lowering preserves this flag. Fuse does not record in the model's `metadata_props` that would be redundant. 

Exporting training metadata (TrainingInfoProto)

- Emitting ONNX `TrainingInfoProto` entries is optional and must be enabled explicitly. Use the CLI flag `--training` (e.g., `fuse onnx -f examples/golden -o onnx --training`) or programmatically pass `emit_training=True` to `FuseLowerer` to emit `ModelProto.training_info` entries when the source contains `@training` metadata and optimizer nodes.


### Usage & examples
- Mark trainable weights:

```fuse
@train weight W: f32[2,2] = [[1.0, 0.0], [0.0, 1.0]]
```

- Mark a frozen constant (not trainable):

```fuse
@frozen const B: f32 = 1e-3
```

- Use nested training config for readability:

```fuse
@training { optimizer: { type = adamw, lr = 3e-4 }, schedule: { type = cosine, warmup = 1000 } }
```

### Testing & examples
- See `tests/training/` for parsing, lowering and export tests.
- Suggested demo: `jupyter/cookbook/train_and_export.ipynb` which trains toy weights (NumPy), writes them into a Fuse snippet, exports to ONNX, and validates with ONNX's ReferenceEvaluator.

## Future-proofing `@training` and loss/algorithm ergonomics 🔧💡
To make training features flexible, ergonomic, and forward-compatible, consider the following recommendations for syntax, semantics, and lowering behavior.

### 1) Explicit loss specification (flexible)
- Allow multiple ways to declare the loss so users can pick what is most ergonomic:
  - `@training { loss: "loss" }` — use an existing graph output named `loss` (default fallback).
  - `@training { loss: loss_fn }` — refer to a named function that computes a scalar loss.
  - `@loss def loss_fn(...)` — decorate a function to mark it as the canonical loss; the training block may then reference it by name.
- Lowering mapping: the chosen loss symbol should produce a `TrainingInfoProto.loss_binding` entry mapping model loss name to the corresponding algorithm graph output when appropriate.

### 2) Built-in optimizer config + override via algorithm (ergonomic and extensible)
- Keep simple optimizer config in `@training` (e.g., `{ optimizer: { type: adamw, lr: 3e-4 } }`) to auto-generate typical optimizer nodes and `update_binding` entries.
- Allow overriding and advanced uses by specifying a custom algorithm:
  - `@training { algorithm = my_alg }` where `my_alg` is a named function or module-level snippet lowered into `TrainingInfoProto.algorithm`.
  - `@algorithm` before a `node` declaration marks it as the canonical algorithm. Example:

```fuse
@algorithm
node my_alg(W: f32, g: f32, lr: f32[1], step: i64) -> f32 {
  # compute new W value and any optimizer state updates, then return
  W_new = ...
  W_new
}
```

Notes on naming: when `lr_input = true` or `step_input = true` are used in module-level `@training`, included literals are created with a qualified, human-friendly name using the module (scope) display (e.g., `module.lr` and `module.step`) so they are unlikely to collide across multiple modules and are easy to identify in the resulting `TrainingInfoProto.algorithm` inputs.
- `@loss` before a `node` declaration marks that function as the training loss; the compiler will bind it to the algorithm via `loss_binding` when referenced in `@training` or inferred from graph outputs.

- If `algorithm` is not provided, `FuseLowerer` synthesizes an algorithm graph using optimizer nodes generated by gradient/optimizer passes.

### 3) Inputs vs constants: dynamic hyperparams & iteration
- Use tight, explicit flags in `@training` to declare which hyperparameters should be inputs to the algorithm graph (syntax: `lr_input = true`, `step_input = true`). Example:

```fuse
@training { optimizer: { type = adamw, lr = 3e-4 }, lr_input = true, step_input = true }
```

- Default behavior: scalar `lr` from a simple numeric config becomes a literal initializer embedded in the model; set `lr_input = true` to expose a dynamic `lr` input to the algorithm graph for schedulers or runtime control. `step_input = true` similarly exposes an iteration/step scalar (`i64`) as an algorithm input.

- Lowering behavior:
  - `lr_input = true` → `FuseLowerer` will create a named `lr` literal and `emit_training_info` will expose it as an algorithm graph input (not an algorithm initializer).
  - `step_input = true` → a named `step` literal (`i64`) will be created and exposed as an algorithm input.

This keeps the DSL tight and explicit while allowing dynamic control of common hyperparameters.

### 4) Initialization and training metadata
- Ensure `TrainingInfoProto.initialization` is always present (empty graph acceptable). Expose a DSL entry to declare initialization strategies (random init, reset step counter, restore checkpoints).
- Expose `training_config` metadata for auditing and runtime (optimizer type, schedules, hyperpars) and keep `model_metadata.trainables` mapping stable and deterministic.

### 5) Name resolution & import alias ergonomics
- Allow loss/algorithm references to resolve via: (a) local symbol name, (b) qualified name, or (c) alias-stripped name (helpful for imported modules). The lowering should implement deterministic resolution rules and clear error messages for ambiguous names.

### 6) Multiple optimizers & per-parameter overrides
- Support `optimizers: [ { selector: "conv.*", optimizer: { type: sgd, lr: 1e-3 } }, { selector: "*", optimizer: { type: adamw, lr: 3e-4 } } ]` to express per-parameter hyperpar overrides ergonomically.
- Lowering should expand selectors and apply deterministic conflict resolution (last-wins or most-specific-wins with documentation).

### 7) Hooks, callbacks, and custom ops (advanced)
- Provide optional `hooks` or `callbacks` entries in `@training` for users to request pre-update/post-update behavior (logging, clamp, clip), or to instruct lowering to emit extra nodes in algorithm/init graphs.

### 8) Backwards compatibility & safety
- Keep simple default behavior (infer `loss` output if available, auto-generate standard optimizers) to preserve existing user workflows.
- Changes should be additive and opt-in. New fields should be ignored by older tool versions gracefully; emitted `TrainingInfoProto` must be validator-friendly (explicit opset imports, training domain opset versioning).

### 9) Tests & examples to add
- DSL parsing tests for `loss`, `algorithm`, `lr_input`, and `optimizers` with selectors.
- Lowering tests ensuring `training_info.algorithm` and `initialization` present, `update_binding` keys resolve, and trainable initializers are not copied into algorithm initializers.
- Golden example demonstrating custom `@algorithm` lowering and dynamic lr via `lr_input`.

> Note: Mapping high-level DSL concepts to ONNX artifacts must be explicit in the spec: `loss` → `loss_binding`, `algorithm` → `TrainingInfoProto.algorithm` GraphProto, `initialization` → `TrainingInfoProto.initialization` GraphProto, `trainables` → model initializers + `update_binding` keys.
